buyer-service

Этот сервис предназначен для пользования покупателями. Здесь покупатели регистрируются, ищут товары, добавляют
в корзины и непосредственно совершают покупки.

Таблицы должны быть реализованы в миграциях Liquibase. Каждая таблица и каждая колонка должны иметь описание.
Каждому внешнему ключу должно быть дано имя (например fk_product_seller). Имя схемы buyer_application, имя базы данных
buyer_database.

Подразумевается, что авторизация и аутентификация пользователей будет реализована в отдельном сервисе.
Запросы к buyer-service и seller-service не будут поступать непосредственно, они будут проксироваться через gateway_service.
Последовательность такова:
1)в gateway_service пользователь (покупатель или продавец) авторизируется и аутентифицируется, выполняет нужный ему запрос;
2)gateway_service направляет запрос в нужный сервис, обогащая его хэдером X-Auth-User-ID, куда помещается UUID пользователя;
3)при обработке запроса данные о пользователе берутся из хэдера X-Auth-User-ID.

Хэдер X-Auth-User-ID не добавляется для эндпоинтов, которые работают с записями пользователей: добавляют, изменяют,
получают список пользователей или данные по конкретному пользователю. Предполагается изначально, что эти
запросы будут приходить от администрации, у простых пользователей не будет возможности через gateway_service
отправить эти запросы (такой подход не вполне верен и в реальном проекте нам следовало бы создать ещё и сервис для
администрации, но времени на это едва ли хватит).


Должны присутствовать следующие контроллеры:
---------------------------------------------------------------------------------------------------------------------
                                Контроллер покупателей
-создание нового пользователя;
-дезактивация пользователя (колонка active в таблице);
-получение общей информации о пользователях по набору фильтров;
-получение подробной информации о конкретном пользователе;
-получение подробной информации пользователем о самом себе;

На всех методах X-Auth-User-ID должен отсутствовать, кроме последнего.
---------------------------------------------------------------------------------------------------------------------
                                Контроллер продавцов
-создание нового пользователя;
-дезактивация пользователя (колонка active в таблице);
-получение общей информации о пользователях по набору фильтров;
-получение подробной информации о конкретном пользователе;

X-Auth-User-ID не требуется.
---------------------------------------------------------------------------------------------------------------------
                                Контроллер товаров
-поиск товаров по фильтрам;
-добавление нового товара. Это действие выполняется продавцом, запрос приходит из seller-service;
-дезактивация товара;
-добавление/убавление количества складских остатков;
-изменение товара (название, описание, цена, категории);

На все эти эндпоинты запросы приходят из seller-service, он же обогащает запросы X-Auth-User-ID продавцов. Исключением
является первый эндпоинт, товары могут смотреть все, X-Auth-User-ID там не требуется.
---------------------------------------------------------------------------------------------------------------------
                                Контроллер заказов
-добавление определённого количества выбранного товара в корзину;
-получение информации о товарах в корзине;
-получение информации об истории покупок;
-удаление из корзины товаров;
-совершение заказа.

Обращаться к этому контроллеру могут только покупатели.
---------------------------------------------------------------------------------------------------------------------

Принцип работы сервиса таков:
-через REST или Kafka (сперва будет только REST) продавец добавляет товар;
-покупатель ищет товары, добавляет в корзину;
-покупатель совершает заказ, покупая товары из корзины. Происходит подсчёт стоимости, происходит проверка наличия товаров
на складе (покупатель мог положить в корзину товар, когда его было достаточно, однако его могли разобрать). Информация
о заказе отправляется в order_service, где непосредственно производится оплата (order_service реализовывать в данном
проекте не будем, просто добавим заглушку).
